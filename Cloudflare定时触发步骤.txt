结论：cron 时间没写错，时区也没错。是 GitHub 自己的定时调度在排队 ——

反证：同一天手动触发（workflow_dispatch）的运行，创建时间和启动时间是同一秒：
  11-17 12:26:56Z 创建 → 12:26:56Z 启动（供应商线）
  11-17 11:30:43Z 创建 → 11:30:43Z 启动（价格线）
所以「外部打 dispatch」是即时的，准时只能靠它。

二、要做的事（两件，约 5 分钟）
============================================================

【第 0 件】控制台在哪里
  网址：https://dash.cloudflare.com
  · 用当初注册 Cloudflare 的邮箱 + 密码登录（这个账号之前建过 medicine-trigger，不是新注册）
  · 忘了密码：登录页点「Forgot your password?」→ 邮箱收重置链接
  · 登录后先看左侧菜单，新版界面叫「Compute (Workers)」，旧版直接叫「Workers & Pages」，
    两种点进去都是同一个 Worker 列表，里面能看到 medicine-trigger

【第 1 件】把 Worker 代码换掉
  1. Cloudflare 控制台 → Workers & Pages → 点你的 medicine-trigger
  2. 右上「编辑代码」（Edit code）
  3. 全选删掉旧内容，把 D:\medicine_grab\cloudflare-worker-trigger.js 的全文粘进去
  4. 点右上「Deploy」（部署）
  新代码会根据 cron 自动分发到三条线，不用手改 workflow 名字。

【第 2 件】加三条 Cron 触发器
  位置：该 Worker → 设置（Settings）→ 触发器（Triggers）→ Cron 触发器 → 添加
  照下面三条加（Cloudflare 的 cron 用 UTC，括号是北京时间，别填错）：

     5 0 * * *      →  北京 08:05   供应商（药通网 + 中香）    跑 6~8 分钟
     35 0 * * *     →  北京 08:35   个人求购（药通网 + 中香）  跑 1~2 分钟
     45 0 * * *     →  北京 08:45   药材价格                   跑约 1 小时

  ⚠️ 价格线原来是 `17 0 * * *`（08:17），2026-11-17 挪到 `45 0 * * *`。
     原因：价格线一跑就是一小时，08:17 会和 08:05 供应商、08:35 求购重叠；
     三个 workflow 共用同一个 Google 服务账号（写请求 60 次/分钟），撞上就 429。
     顺序改成 供应商 → 求购 → 价格，价格是最后一条长活，跑完就收，不影响别人。
     ⚠️ 所以旧的那条 `17 0 * * *` 一定要删除，否则 08:17 还会白跑一次（会被"今天已抓过"跳过，但很乱）。

  ⚠️ 加之前先把旧的多余 cron 删掉。之前价格线在 UTC 00:17、03:17、11:30 都被触发过
     （11:30Z 是北京 19:30，纯属白跑），新版只保留上面三条。

  康美那条不在这里：它由阿里云函数每天 07:50 抓完直接提交 CSV，不走 GitHub 触发。

三、怎么验证
============================================================

1. 浏览器打开 Worker 网址，返回「✅ 成功！已触发 daily-crawl.yml」= 令牌和仓库名都对。
   ⚠️ 如果返回的是「GitHub 已收到触发请求」（没有具体文件名）= 跑的仍是旧代码，回去点 Deploy。
   想单独测哪条线，加参数：
      网址/?wf=supplier     供应商
      网址/?wf=price        价格
      网址/?wf=purchase     求购
   想看 Worker 网址在哪：该 Worker → 设置（Settings）→ 域和路由（Domains & Routes），
   形如 https://medicine-trigger.你的子域.workers.dev
2. 去 GitHub → Actions，看新运行的事件是不是 workflow_dispatch、时间是不是刚刚。
3. 第二天早上 08:15 / 08:40 / 09:50 各刷新一次，应该能看到三条都已跑完。

四、价格线「同一天不重抓」是怎么生效的
============================================================

价格线 workflow 第一步会执行 ci_state.py check，读仓库根目录的 crawl_state.json：
  · 里面记着 date（北京时间）、rows（行数）、meds（味数）
  · 如果 date 就是今天，且 rows ≥ 300 → 本次直接跳过，整条链只花 20 秒
  · 跑完「抓取 → 历史价 → 建图 → 推送校验」全部成功后，最后一步才写这个文件

所以现在同一天最多跑一次：
  早上 08:45 Cloudflare 触发 → 正常跑完约 50~60 分钟 → 写入 crawl_state.json
  下午 GitHub 的 cron 迟到触发 → 第一步读到「今天已完成」→ 立即跳过（不再白跑）

要注意的两点：
  · 「推送失败」不算完成 —— 记录步骤排在推送校验后面，失败时不会写状态，
    下午那次迟到的 cron 会当成没抓过，再试一次（这是故意的兜底）。
  · 想强制重抓：GitHub 网页 Run workflow 时把 force 填 true；
    本地跑脚本不受影响，本地没有 crawl_state.json 就照常抓。

============================================================
五、顺带说明：供应商线 / 求购线没有加这个跳过
============================================================

供应商和求购数据每天全量不同（有新供货、旧的过期），同一天跑两次只是慢一点，
不会写错数据，而且早上那次万一抓漏了，下午那次重跑正好当兜底。
如果你也想让它们「一天只跑一次」，告诉我，加的是同一套机制。
